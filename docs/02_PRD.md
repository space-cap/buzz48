# [PRD] 버즈48 (Buzz48) : 48시간 타임어택 실시간 게시판 플랫폼

> **버전**: v1.1 | **작성일**: 2026-07-03 | **기반 문서**: 서비스 기획서 v2.1

---

## 0. 우선순위 정의

| 등급 | 정의 |
| :--- | :--- |
| **P0** | 없으면 서비스가 성립하지 않는 핵심 기능. 출시 필수. |
| **P1** | 상용 서비스 품질·수익화에 필요하나, 기술적으로 P0 이후 순차 배포 가능. |
| **P2** | 초기 트래픽 확보 후 데이터 기반으로 고도화할 기능. |

## 1. 세션 및 닉네임 시스템 (P0)

### 1.1 User Story
사용자는 회원가입 없이 접속 즉시 게시글 작성 및 채팅 참여를 할 수 있어야 한다.

### 1.2 요구사항

| ID | 요구사항 |
| :--- | :--- |
| SES-01 | 최초 접속 시 서버는 UUID v4 기반 익명 세션을 발급하고, 클라이언트는 이를 쿠키(HttpOnly, Secure) 및 로컬스토리지에 이중 저장한다. |
| SES-02 | 닉네임은 `[상태·감정 수식어] + [명사]` 조합 사전에서 서버가 랜덤 생성하여 세션에 매핑한다. 조합 사전은 최소 100×100 = 10,000개 이상의 조합을 만들 수 있도록 구성한다. |
| SES-03 | 사용자는 프로필 팝업에서 닉네임을 직접 수정할 수 있다. 익명 상태에서는 로컬 세션에만 저장한다. |
| SES-04 | 소셜 로그인(구글·카카오·네이버) 연동 시, 기존 익명 세션의 닉네임·참여 이력을 로그인 계정에 귀속시킨다. |

### 1.3 Edge Case (반드시 정의 필요)

| 상황 | 처리 방식 |
| :--- | :--- |
| 쿠키 삭제 후 재접속 | 새 UUID 세션 발급. 기존 세션과의 연결 없음(익명 특성상 불가피). 로그인 유저에게 소셜 로그인을 유도하는 배너 노출로 이탈 방지. |
| 동일 유저가 PC/모바일 등 여러 기기로 접속 | 비로그인 상태에서는 기기별로 별도 세션·닉네임 부여됨을 정책으로 명시(기기 간 동기화 없음). 로그인 시에만 동기화. |
| 닉네임 중복 (동일 게시물 내 동일 닉네임) | 닉네임은 전역 유일값이 아님. 채팅 UI에서는 세션 ID 기반 색상 태그를 병기하여 동일 닉네임 유저 구분. |
| 부적절 닉네임 자동 생성 (조합 결과가 욕설이 되는 경우) | 조합 사전 등록 시 금칙어 교차 필터링을 1회 실행하여 사전 자체에서 제거. 커스텀 닉네임 변경 시에도 5.1 금칙어 필터 동일 적용. |
| 세션 만료 정책 | 비로그인 세션은 마지막 활동 기준 90일 미접속 시 자동 폐기(개인정보보호법 IP 로그 30일 보관 정책과는 별개로, 세션 자체의 보관 기한). |

## 2. 게시물 작성 및 분류 (P0)

### 2.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| POST-01 | 사용자는 제목(최대 100자), 본문(최대 3,000자, 이미지 최대 4장), 카테고리(단일 선택)를 입력하여 게시물을 작성한다. |
| POST-02 | 생성 즉시 `created_at` 타임스탬프가 서버 시각(UTC) 기준으로 기록되며, 이 시각이 24시간/48시간 카운트다운의 기준점이 된다. |
| POST-03 | 동일 세션(비로그인) 또는 동일 계정(로그인)당 1시간에 최대 3개까지 생성 가능. 초과 시 작성 버튼 비활성화 및 "다음 생성 가능 시각: HH:MM" 안내. |
| POST-04 | 생성과 동시에 해당 게시물은 자동으로 `LIVE` 상태가 되며 실시간 채팅을 위한 웹소켓 채널이 개설된다. |

### 2.2 Edge Case

| 상황 | 처리 방식 |
| :--- | :--- |
| 생성 중 네트워크 끊김으로 서버는 저장했으나 클라이언트가 응답을 못 받은 경우 | 클라이언트에 멱등키(idempotency key)를 발급하여 중복 생성 방지. 동일 키로 재요청 시 기존 생성된 게시물 정보 반환. |
| Rate Limit(1시간 3개) 리셋 기준 | 고정 시각(정각) 리셋이 아닌, **최초 생성 시각으로부터 60분 슬라이딩 윈도우**로 계산. |
| 이미지 업로드 콘텐츠에 대한 사전 검수 | 업로드 즉시 노출(사후 신고 기반)이 기본이나, AI 이미지 필터(성인물·폭력물 감지)를 업로드 파이프라인에 동기 적용하여 명백한 위반은 즉시 차단. |

## 3. 실시간 채팅 (WebSocket) (P0)

### 3.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| CHAT-01 | `LIVE` 상태의 게시물에서만 메시지 전송이 가능하며, 최대 500자까지 입력 가능하다. |
| CHAT-02 | 메시지는 전송 즉시 해당 게시물에 접속한 모든 클라이언트에 브로드캐스트되며, 목표 지연시간은 200ms 이내(P95 기준)로 한다. |
| CHAT-03 | 특정 메시지에 대한 답장(Reply) 기능 지원. 원문 메시지 일부(최대 50자)를 인용 형태로 상단에 표시. |
| CHAT-04 | 이모지 반응(👍 ❤️ 😂 😡)은 메시지당 사용자 1인 1반응만 허용하며, 재클릭 시 취소 처리. |

### 3.2 Edge Case (필수 — 실시간 서비스 품질을 좌우)

| 상황 | 처리 방식 |
| :--- | :--- |
| 네트워크 순간 끊김 후 재연결 | 클라이언트는 마지막 수신 메시지 ID를 기준으로 재연결 시 `sync` 요청을 보내고, 서버는 누락 구간 메시지를 일괄 전송(재연결 시 전체 재로딩 금지). |
| 메시지 전송 중 게시물이 LIVE→READ로 전환된 경우 | 서버는 전송 요청 시각을 기준으로 판정. `created_at + 24h` 이전에 서버가 수신한 메시지는 정상 처리, 이후 도착분은 거부 후 클라이언트에 "채팅이 종료되었습니다" 안내. |
| 동시 대량 접속 (HOT 게시물 폭주) | 게시물 단위로 WebSocket 커넥션을 샤딩하고, Redis Pub/Sub으로 서버 인스턴스 간 메시지를 중계하여 단일 서버 병목 방지(아키텍처 문서에서 상세화). |
| 답장 대상 메시지가 이미 삭제(신고 처리)된 경우 | "삭제된 메시지입니다"로 인용문 대체, 답장 기능 자체는 유지. |
| 이모지 반응 카운트의 원자성 | Redis INCR/DECR 기반 원자적 연산 사용, 동시 다발 클릭 시 카운트 정합성 보장. |

## 4. 콘텐츠 수명주기 (LIVE → READ → DELETE) (P0)

이 서비스의 핵심 로직이므로 시간 판정 기준을 명확히 한다.

### 4.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| LIFE-01 | 판정 기준 시각은 **서버 시각(UTC) 기준**이며, 클라이언트 로컬 시각은 표시용으로만 사용한다. |
| LIFE-02 | `created_at` 기준 0~24시간: `LIVE`. 24~48시간: `READ`. 48시간 초과: `DELETE`(영구 삭제). |
| LIFE-03 | 상태 전환은 실시간 배치 워커가 **10초 주기**로 스캔하여 상태값을 갱신하고, 해당 게시물에 접속 중인 클라이언트에 WebSocket 이벤트(`post_state_changed`)로 즉시 통지한다. |
| LIFE-04 | `DELETE` 시점에 메시지·게시글·이미지·신고 이력을 포함한 모든 관련 데이터를 파기한다. 단, 5.3 법적 요건에 따른 신고 처리 중인 콘텐츠는 예외 처리(§4.3 참조). |

### 4.2 Edge Case

| 상황 | 처리 방식 |
| :--- | :--- |
| 정확히 24:00:00 경계에 입력 중이던 유저 | 서버는 메시지 **수신 시각** 기준으로 판정(§3.2와 동일 원칙). UX 측면에서 23:59:30부터 입력창 상단에 "곧 읽기 전용으로 전환됩니다" 카운트다운 경고 배너 노출. |
| 배치 워커 장애로 전환이 지연된 경우 | 전환 시각은 항상 `created_at` 기준 계산값이 진실(Source of Truth). 워커는 상태 캐시(Redis)만 갱신하는 역할이므로, 워커가 일시 중단되어도 실제 쓰기 권한 체크는 매 메시지 전송 시점에 `created_at`을 재계산하여 이중 검증한다. |
| 신고 처리 중인 메시지가 48시간 경과로 삭제 대상이 된 경우 | 법적 분쟁·수사기관 요청 가능성이 있는 콘텐츠는 별도 아카이브 테이블로 이관 후 원본은 파기(익명 처리된 로그만 최대 30일 보관, §5.3 정책과 일치). |
| READ 상태에서 스크롤 성능 (오래된 대량 메시지 로딩) | 커서 기반 페이지네이션 필수. 무한 스크롤 시 최초 로딩은 최근 50개만, 이전 메시지는 스크롤 시 추가 로딩. |
| DELETE 이후 해당 URL 재접속 시 | 404가 아닌 "이 게시물은 종료되어 사라졌습니다" 전용 페이지 노출 + 관련 카테고리의 현재 LIVE 게시물 추천(이탈 방지 겸 SEO 활용). |

## 5. HOT 알고리즘 (P0)

### 5.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| HOT-01 | Score = (현재 동접자 수 × 0.5) + (최근 5분간 채팅 수 × 0.3) + (최근 5분간 이모지 반응 수 × 0.2) |
| HOT-02 | 스코어는 **10초 주기**로 전체 LIVE 게시물을 대상으로 재계산하며, Redis Sorted Set으로 관리한다. |
| HOT-03 | 상위 3개 게시물을 메인 화면 상단 카드에 노출한다. |

### 5.2 Edge Case (계산식의 모호함 제거)

| 항목 | 명확화 |
| :--- | :--- |
| "동접자 수"의 정의 | WebSocket 연결이 유지되고 있는 세션 수. 단순 페이지 조회가 아닌 **실제 소켓 연결 상태**를 기준으로 하며, 백그라운드 탭(비활성) 여부는 구분하지 않음(v1.0 기준, 추후 고도화 시 활성 tab 감지 추가 검토 — P2). |
| "최근 5분간"의 윈도우 방식 | **슬라이딩 윈도우**(현재 시각 기준 직전 5분)로 계산. 고정 버킷(00~05분, 05~10분 식) 방식은 채택하지 않음 — 갱신 직후 스코어가 급락하는 부자연스러움 방지. |
| 신규 생성 게시물의 초기 노출 | 생성 직후 채팅·반응 데이터가 없어 Score가 0에 가까움 → HOT 진입이 구조적으로 불리. **최초 5분간은 "NEW" 배지와 함께 카테고리 탭 상단에 별도 노출**하여 초기 트래픽 확보 기회 제공(HOT 카드와는 별도 슬롯). |
| 어뷰징 방어 세부 기준 | 동일 세션에서 짧은 시간 내 동일 게시물 재입장/퇴장을 반복하여 동접자 수를 부풀리는 경우, 서버는 세션별 마지막 연결 시각을 기준으로 **60초 내 재연결은 동일 접속으로 간주**(중복 카운트하지 않음). |
| 급격한 스코어 상승 플래그 기준 | 직전 계산 대비 Score가 **300% 이상 증가 + 절대값 기준치(예: 50점) 초과** 시 자동 플래그. 두 조건 동시 충족 시에만 플래그(신생 게시물의 정상적 급성장까지 오탐하지 않도록). |

## 6. 신고 및 제재 (P0)

### 6.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| MOD-01 | 모든 메시지·게시글에 신고 버튼 제공. 사유: 욕설/혐오, 허위정보, 스팸/도배, 개인정보 노출. |
| MOD-02 | 금칙어 DB 1차 필터링(전송 전 서버단 차단) + AI 맥락 감지 2차 필터링(전송 후 비동기 스캔). |
| MOD-03 | 단시간 내 다수 신고 접수 시 자동 블라인드 처리 후 관리자 검토 큐 전송. |

### 6.2 Edge Case

| 항목 | 명확화 |
| :--- | :--- |
| "단시간 내 다수 신고"의 정량 기준 | **동일 메시지에 대해 서로 다른 세션 5건 이상, 10분 이내** 접수 시 자동 블라인드. 동일 세션의 중복 신고는 1건으로 카운트. |
| 제재 누적 기준(1차→2차→3차)의 리셋 정책 | 위반 이력은 **최근 90일 롤링 윈도우**로 카운트. 90일간 위반 없으면 카운트 리셋. 단, 영구 IP 차단(3차) 이력 자체는 영구 보관. |
| 블라인드 처리된 메시지의 채팅 흐름 표시 | 완전 삭제가 아닌 "신고에 의해 숨겨진 메시지입니다"로 대체 표시(답장 인용 관계 보존을 위해 즉시 물리 삭제하지 않고, 관리자 검토 후 최종 삭제 확정 시 파기). |
| AI 맥락 필터가 오탐(정상 메시지 차단)한 경우 | 이의제기 버튼 제공, 이의제기 접수 시 24시간 내 관리자 재검토. 재검토 전까지는 비노출 유지(선 차단 후 검토 원칙). |
| 관리자 검토 큐의 SLA | 상용 서비스 기준 **접수 후 4시간 이내 1차 검토** 목표(야간 시간대는 익일 오전 포함하여 12시간 이내). 초기에는 수동 검토 인력 확보 필요 — 운영 문서에서 별도 정의. |

## 7. 알림 (Notification) (P1)

### 7.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| NOTI-01 | HOT 상위 3위 진입 알림, 만료 임박(1시간 전) 알림, 답장/반응 알림을 FCM으로 발송한다. |

### 7.2 Edge Case

| 항목 | 명확화 |
| :--- | :--- |
| 알림 중복/과다 발송 방지 | 동일 유저에게 동일 게시물에 대해 동일 유형 알림은 **1일 1회로 제한**(예: HOT 진입 알림은 게시물당 최초 1회만). |
| 비로그인 유저의 푸시 알림 | 웹 푸시(브라우저 알림 권한) 기반으로 처리하며, 앱 출시(Phase 3) 이전까지는 FCM Web Push로 한정. 로그인 유저는 추가로 카카오 알림톡 연동 검토(P2). |
| 만료 임박 알림의 기준 시각 | "관심 표시"(북마크) 여부와 무관하게 **본인이 채팅을 남긴 게시물**은 자동으로 알림 대상에 포함. 북마크는 별도 옵션. |

## 8. 공유 및 바이럴 (P1)

### 8.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| SHARE-01 | OG 태그에 실시간 잔여시간을 동적 삽입("이 게시물은 N시간 M분 후 사라집니다"). |
| SHARE-02 | 종료 직전(READ 전환 임박) 인기 채팅 발췌를 이미지 카드로 자동 생성. |

### 8.2 Edge Case

| 항목 | 명확화 |
| :--- | :--- |
| OG 태그 동적 렌더링 방식 | 카카오톡·트위터 등 크롤러는 캐시를 사용하므로, OG 이미지에 잔여시간을 **분 단위가 아닌 "N시간 이내" 구간(예: 1시간 이내/6시간 이내/24시간 이내)**으로 표기하고 캐시 TTL을 짧게(5분) 설정하여 절충. |
| 인기 채팅 발췌 카드 생성 기준 | READ 전환 **직전 1시간 시점**에 배치로 이모지 반응 수 상위 3개 메시지를 선정하여 자동 생성. 개인정보(실명·연락처 패턴) 포함 메시지는 자동 제외 필터 적용. |

## 9. 프리미엄 게시물 — 유료 입장 (P1, 수익화 핵심)

### 9.1 요구사항

| ID | 요구사항 |
| :--- | :--- |
| PAY-01 | 인증된 개설자(전문가·인플루언서)가 유료 게시물을 개설할 수 있다. |
| PAY-02 | 참여자는 인앱 재화(팝콘/별)로 입장료를 결제한다. 플랫폼은 20~30% 수수료를 수취한다. |

### 9.2 Edge Case (수익화 기능이므로 반드시 사전 정의)

| 항목 | 명확화 |
| :--- | :--- |
| 결제 후 환불 정책 | 입장 후 **채팅 미참여 상태에서 5분 이내** 요청 시 100% 환불. 그 외에는 원칙적으로 환불 불가(디지털 콘텐츠 특성상 전자상거래법 예외 조항 검토 필요 — 법무 문서에서 확정). |
| 게시물 개설자가 조기 종료/삭제한 경우 | 잔여 시간에 비례하여 참여자에게 자동 환불(예: 24시간 중 6시간 만에 삭제 시 75% 환불). |
| 정산 주기 및 최소 정산액 | 익월 15일 정산 원칙, 최소 정산액 1만원 미만은 익익월로 이월. |
| 개설자 인증 기준 | 초기에는 수동 심사(SNS 팔로워 수, 본인 인증) 기반. 자동화된 인증 배지 시스템은 P2. |
| 인앱 재화의 법적 성격 | 선불전자지급수단에 해당할 경우 전자금융거래법상 등록 의무 발생 가능 — **법무 검토 전까지 개발 착수 보류 권장**(§10 참조). |

## 10. 비기능 요구사항 (Non-Functional Requirements)

| 구분 | 요구사항 |
| :--- | :--- |
| **성능** | 메시지 브로드캐스트 지연 200ms 이내(P95). 게시판 목록 페이지 최초 로딩 1.5초 이내(LCP 기준). |
| **가용성** | 목표 가동률 99.9%(월 다운타임 약 43분 이내). WebSocket 서버는 최소 2개 이상 인스턴스로 이중화. |
| **확장성** | 동시 접속 10만 세션까지 수평 확장 가능한 구조로 설계(Redis Cluster, WebSocket 서버 오토스케일링). |
| **보안** | 세션 토큰 HttpOnly/Secure 쿠키, 모든 API HTTPS 강제, XSS 방지를 위한 채팅 메시지 sanitize 필수. |
| **개인정보** | IP 로그 최대 30일 보관 후 자동 파기 배치(§5.3 기획서 정책과 일치). GDPR 대상 유저 식별 시 별도 삭제 요청 프로세스 지원. |

## 11. 결정 보류 항목 (Open Questions — 개발 착수 전 확정 필요)

문서 작성 중 발견된, 정책적 판단이 필요한 항목입니다. 개발 착수 전 확정을 권장합니다.

1. **인앱 재화(팝콘/별)의 법적 성격** — 전자금융거래법상 선불전자지급수단 등록 대상 여부. 상용 서비스로 처음부터 간다면 이 부분은 법무 검토 없이는 §9 기능 개발에 착수하지 않는 것을 권장합니다.
2. **동접자 수 카운트 기준**(§5.2)의 "활성 탭 여부 미구분" 정책 — 이후 광고 CTR·과금 근거로 쓰일 수 있는 지표이므로, 광고주 대상 리포팅 시 이 정의를 명시할 필요가 있습니다.
3. **관리자 검토 인력 확보 방안**(§6.2 SLA) — 1인/소수 개발 체제에서 4시간 SLA를 지키려면 초기 아웃소싱 또는 3교대 없는 대체 운영안이 필요합니다.
4. **프리미엄 게시물 환불 규정**(§9.2)의 전자상거래법 적합성 — 실제 서비스 약관에 반영 전 법률 자문 권장.

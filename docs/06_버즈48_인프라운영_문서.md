# [인프라/운영 문서] 버즈48 (Buzz48)

> **버전**: v1.0 | **작성일**: 2026-07-03 | **기반 문서**: 시스템 아키텍처 설계서 v1.0, PRD v1.0
> **인프라 현황 반영**: Redis는 오라클 클라우드 Always Free 인스턴스에 Docker로 직접 배포(아키텍처 문서 §7의 ElastiCache 대체안). 이에 맞춰 모니터링·장애 대응 항목을 조정.

---

## 1. 인프라 구성 현황

| 구성 요소 | 배포 위치 | 비고 |
| :--- | :--- | :--- |
| Redis | 오라클 클라우드 Always Free VM (Docker) | AWS ElastiCache 대비 정액(무료) 운영, 직접 관리 필요 |
| WebSocket 서버 / REST API / 워커 | 아키텍처 문서 §7 기준 AWS ECS/Fargate (또는 초기엔 동일 오라클 클라우드 VM에 컨테이너로 함께 배포 가능) | 오라클 클라우드로 전체 통합 시 네트워크 지연 최소화 장점 |
| PostgreSQL | Neon(개발) → 운영 전환 시 Neon 유료 플랜 또는 별도 관리형 DB | DB 설계서 §0 참조 |

> **주의**: Redis가 오라클 클라우드에, 애플리케이션 서버가 AWS에 있으면 리전 간 네트워크 왕복 지연이 아키텍처 문서 §2에서 목표한 200ms(P95) 예산을 잠식할 수 있습니다. **애플리케이션 서버도 당분간 오라클 클라우드에 함께 두거나, 같은 리전/가용영역으로 맞추는 것을 권장**합니다.

## 2. 모니터링 및 알러팅

### 2.1 모니터링 대상 지표

| 계층 | 지표 | 임계치(초기 기준값) |
| :--- | :--- | :--- |
| Redis (오라클 VM) | 메모리 사용률 | 80% 초과 시 경고 |
| Redis (오라클 VM) | 커넥션 수 | Always Free VM 스펙 대비 70% 초과 시 경고 (사양이 제한적이므로 AWS ElastiCache보다 여유 적음) |
| WebSocket 서버 | 활성 커넥션 수 | 인스턴스당 1만 커넥션 초과 시 오토스케일 트리거(아키텍처 문서 §7) |
| WebSocket 서버 | 메시지 브로드캐스트 지연 | P95 200ms 초과 시 경고 (PRD §10) |
| API 서버 | 5xx 에러율 | 1% 초과 시 경고 |
| PostgreSQL | 커넥션 풀 사용률 | 80% 초과 시 경고 |
| 배치 워커 | Lifecycle/Purge/HOT Score Worker 마지막 실행 시각 | 예상 주기(10초) 대비 3배 이상 지연 시 경고 |

### 2.2 모니터링 도구

- **초기 단계**: 오라클 클라우드 자체 모니터링(OCI Monitoring) + CloudWatch(AWS 리소스용)로 시작. 별도 비용 없이 기본 지표 확보 가능.
- **트래픽 증가 후**: Grafana + Prometheus 자체 구축(오라클 클라우드 Always Free VM에 함께 배포 가능, 추가 비용 없음) 또는 Datadog 등 APM 유료 도입 검토.
- **알림 채널**: 초기엔 Slack 또는 카카오톡 알림톡(개발자 본인에게 발송)으로 충분. 다인 운영 전환 시 PagerDuty 등 온콜 도구 검토.

### 2.3 Redis 자체 운영 특이사항 (오라클 클라우드 Docker 배포)

관리형 서비스가 아니므로 아래 항목은 **직접 챙겨야 합니다**.

- **백업**: `redis-cli --rdb` 또는 `BGSAVE`로 주기적 스냅샷을 별도 스토리지(오브젝트 스토리지 등)에 백업. LIVE 데이터는 최대 24시간 내 소멸되는 특성상 백업의 실효성은 낮지만, 세션/HOT 랭킹 등 서비스 연속성에 필요한 키는 별도 백업 대상으로 관리.
- **버전 업그레이드**: 관리형 서비스와 달리 자동 패치가 없으므로, 보안 패치는 수동으로 Docker 이미지 갱신 및 재기동 필요.
- **장애 시 복구**: 단일 인스턴스 구조(Redis Cluster 미적용 시)이므로 인스턴스 장애 시 단일 장애점(SPOF)이 됩니다. 초기 트래픽 단계에서는 감수 가능하나, HOT 랭킹·세션 데이터 유실 시 서비스 전체 영향이 있으므로 **최소한 일 1회 스냅샷 + 재기동 스크립트**는 준비 권장.

## 3. 장애 대응 Runbook

### 3.1 Redis(오라클 VM) 다운

1. 헬스체크 실패 감지(모니터링 알림 수신) → 즉시 Docker 컨테이너 상태 확인(`docker ps`, `docker logs`)
2. 컨테이너 재기동 시도(`docker restart`)
3. 재기동 실패 시 최근 스냅샷으로 복구
4. 복구 중에는 WebSocket 서버가 Redis 연결 실패를 감지해 클라이언트에 "일시적 오류" 안내 후 재연결 재시도 로직 동작(아키텍처 문서 §2.3 재연결 로직 활용)
5. **영향 범위**: LIVE 채팅 송수신 전면 중단. HOT 랭킹 갱신 중단(단, PRD §4.2 이중 검증 원칙 덕분에 방 상태 판정 자체는 영향받지 않음 — 캐시가 없어도 `created_at` 기준 재계산 가능)

### 3.2 WebSocket 서버 인스턴스 다운

- ALB 헬스체크로 자동 제외, 클라이언트 재연결 로직으로 흡수(아키텍처 문서 §9와 동일)

### 3.3 PostgreSQL(Neon) 장애

- Neon 자체 장애 대시보드 확인 → 서비스 상태 페이지 구독
- READ 상태 방 조회만 일시 영향, LIVE 채팅에는 영향 없음(Write-Behind 구조 덕분)

### 3.4 배치 워커 중단 (Lifecycle/Purge/HOT Score)

- PRD §4.2 이중 검증 원칙에 의해 **Lifecycle Worker가 중단돼도 실제 서비스 로직(쓰기 권한 판정)은 정상 동작**. 캐시 갱신만 지연됨.
- Purge Worker 중단 시 48시간 경과 데이터가 삭제되지 않고 누적 — 개인정보 보관 기한(§법무 체크리스트 §4) 위반 리스크가 있으므로 **다른 워커보다 우선 복구**.

## 4. 콘텐츠 모더레이션 운영 매뉴얼

### 4.1 관리자 검토 큐 운영

PRD §6.2에서 정의한 SLA(접수 후 4시간 이내 1차 검토, 야간은 12시간 이내)를 1인/소수 체제에서 지키기 위한 운영 방안:

- **초기 단계(트래픽 낮을 때)**: 개발자 본인이 하루 3~4회(출근 직후, 점심, 저녁, 취침 전) 관리자 검토 큐를 직접 확인.
- **트래픽 증가 시**: 크몽·숨고 등에서 파트타임 모더레이터를 시간제로 고용하거나, 검토 큐 알림을 카카오톡으로 즉시 수신하도록 설정해 대응 속도 확보.
- 검토 큐 적재 시 자동 알림(Slack/카카오톡) 발송을 최우선 구축 항목으로 권장(개발 비용 낮고 SLA 준수에 직결).

### 4.2 AI 필터 오탐 대응

- 이의제기(API 명세서 §2.4 `POST /reports/{id}/appeal`) 접수 시 24시간 내 재검토 원칙(PRD §6.2).
- 오탐 패턴이 반복되면 금칙어 DB 또는 AI 필터 룰을 주기적으로 튜닝(월 1회 검토 권장).

## 5. 배포 파이프라인 (권장안)

- **CI/CD**: GitHub Actions → Docker 이미지 빌드 → 오라클 클라우드(초기) 또는 AWS ECR/ECS(확장 후)로 배포
- **배포 전략**: WebSocket 서버는 무상태 설계이므로 **Rolling 배포**(구 버전 인스턴스를 순차적으로 신 버전으로 교체) 적용 가능, 다운타임 없이 배포
- **DB 마이그레이션**: Neon 브랜칭을 활용해 스테이징 브랜치에서 마이그레이션 먼저 검증 후 운영 반영(§2 이전 대화에서 논의한 워크플로우)

## 6. 운영 비용 관리 체크리스트

| 항목 | 현재 상태 | 확인 필요 시점 |
| :--- | :--- | :--- |
| Redis (오라클 클라우드) | Always Free | 트래픽 증가로 Free 스펙 초과 시 유료 인스턴스 전환 또는 관리형 서비스(ElastiCache) 재검토 |

| AWS(WebSocket/API 서버) | 미정 | 오라클 클라우드로 통합 배포할지, AWS로 분리할지 결정 필요 — §1 네트워크 지연 이슈와 함께 판단 |

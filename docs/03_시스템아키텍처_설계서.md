## 1. 아키텍처 개요

### 1.1 설계 원칙

1. **읽기/쓰기 경로 분리** — LIVE 상태(쓰기 밀집)와 READ 상태(읽기 위주)는 서로 다른 저장소·처리 방식을 사용한다(PRD §4).
2. **상태는 계산 가능해야 한다** — 방의 LIVE/READ/DELETE 상태는 캐시(Redis)에 의존하지 않고 언제든 `created_at`으로부터 재계산 가능해야 한다(PRD §4.2 이중 검증 원칙).
3. **수평 확장 우선** — WebSocket 서버는 무상태(stateless)로 설계하고, 세션 상태는 Redis에 위임하여 인스턴스 추가만으로 확장 가능하게 한다.
4. **장애 격리** — HOT 알고리즘, 알림, 신고 처리 등 부가 기능은 핵심 채팅 경로와 장애가 전파되지 않도록 분리한다.

### 1.2 전체 구성 요소

| 계층 | 구성 요소 | 역할 |
| :--- | :--- | :--- |
| **Frontend** | **Next.js (TypeScript)** | SSR/SSG, OG 태그 동적 생성, 실시간 채팅 UI, HOT 랭킹 UI |
| Edge | CloudFront CDN | 정적 자산, OG 이미지 카드, 이미지 캐싱 |
| API Gateway | ALB (Application Load Balancer) | WebSocket Sticky 없이 라우팅(무상태 서버 전제), REST API 라우팅 |
| 실시간 계층 | **WebSocket 서버 (Go + Gorilla WebSocket)**, N개 인스턴스 | 채팅 송수신, 접속자 카운트 |
| 메시지 브로커 | Redis Pub/Sub (또는 별도 NATS 클러스터) | WebSocket 서버 간 메시지 중계 |
| 인메모리 계층 | Redis Cluster | LIVE 메시지 큐, HOT 스코어 Sorted Set, 세션, Rate Limit 카운터 |
| 배치 워커 | **Lifecycle Worker, Purge Worker, HOT Score Worker (Go)** | 상태 전환, 데이터 파기, 스코어 재계산 (모두 10초~수 분 주기) |
| 영속 계층 | PostgreSQL (Primary + Read Replica) | READ 상태 아카이브, 유저/결제/신고 데이터 |
| **REST API 서버** | **Go (Fiber 프레임워크)** | 방 생성, 로그인, 결제, 신고 등 비실시간 요청 처리 |
| 외부 연동 | FCM, PG사, 소셜 로그인 Provider | 알림, 결제, 인증 |

## 2. 실시간 채팅 아키텍처 (WebSocket 확장 전략)

PRD §3.2에서 정의한 "동시 대량 접속 시 단일 서버 병목 방지" 요구사항을 구현하는 핵심 구조입니다.

### 2.1 문제 정의

WebSocket은 REST와 달리 커넥션이 유지되는 stateful 특성이 있어, 단순히 서버를 여러 대 띄운다고 자동으로 확장되지 않습니다. A 서버에 연결된 유저가 보낸 메시지를 B 서버에 연결된 유저에게도 전달해야 합니다.

### 2.2 해결 구조: Redis Pub/Sub 기반 팬아웃

1. 클라이언트는 ALB를 통해 임의의 WebSocket 서버 인스턴스에 연결된다(어느 인스턴스든 무관 — 무상태).
2. 메시지 전송 시, 해당 서버는 메시지를 **PostgreSQL/Redis에 저장하는 동시에 Redis Pub/Sub 채널(`room:{room_id}`)에 발행**한다.
3. 모든 WebSocket 서버 인스턴스는 자신에게 연결된 클라이언트가 속한 방들의 채널을 구독하고 있으며, 발행된 메시지를 수신하는 즉시 해당 방에 연결된 자신의 클라이언트들에게 브로드캐스트한다.
4. 이 구조로 어느 서버에 붙어있든 동일한 메시지를 동일한 지연시간 내에 수신한다.

### 2.3 재연결 및 메시지 유실 방지 (PRD §3.2 대응)

- 클라이언트는 마지막으로 수신한 `message_id`를 로컬에 보관한다.
- 재연결 시 `sync(last_message_id)` 요청을 보내면, 서버는 Redis LIVE 큐(최근 24시간 이내 메시지가 저장된 List/Stream)에서 누락 구간만 조회하여 일괄 전송한다.
- Redis Stream(`XADD`/`XRANGE`)을 사용하면 메시지 ID가 시간 순서를 보장하는 자동 증가값이라 이 구간 조회가 자연스럽다. **List보다 Stream 구조를 권장.**

### 2.4 HOT 방 폭주 대비 샤딩

- 동접자 수가 급증하는 특정 방(HOT 상위권)은 해당 채널 구독자가 모든 WebSocket 인스턴스에 집중될 수 있다.
- 1만 명 이상 동접이 몰리는 극단적 상황 대비: 방 단위가 아닌 **방+파티션 단위**로 채널을 세분화(`room:{room_id}:{partition}`)하고, 클라이언트를 파티션에 라운드로빈 배정하는 구조를 P1 이후 도입 검토(초기 트래픽 수준에서는 불필요 — 과설계 주의).

## 3. 콘텐츠 수명주기 처리 (LIVE → READ → DELETE)

PRD §4의 로직을 실제 시스템으로 구현하는 흐름입니다.

### 3.1 데이터 흐름

- **LIVE (0~24h)**: 메시지는 Redis Stream에 저장되며, 동시에 PostgreSQL에도 비동기 쓰기(Write-Behind)로 이중화한다. 읽기는 Redis에서 우선 처리해 초고속 응답을 보장한다.
- **READ (24~48h)**: Lifecycle Worker가 상태를 전환하는 시점에, 해당 방의 Redis Stream 데이터가 PostgreSQL에 완전히 반영되었는지 확인 후 Redis 큐를 정리(TTL 만료 또는 명시적 삭제)한다. 이후 조회는 전량 PostgreSQL(Read Replica)에서 처리한다.
- **DELETE (48h~)**: Purge Worker가 관련 테이블(메시지, 게시글, 이미지, 신고 이력)을 삭제한다. 단 진행 중인 신고 건은 별도 아카이브 테이블로 먼저 이관한다(PRD §4.2).

### 3.2 이중 검증 원칙의 구현

PRD §4.2에서 "워커 장애 시에도 실제 쓰기 권한은 매 메시지 전송 시점에 재계산"하도록 정의했습니다. 이를 위해:

- 방 상태(`state`)는 Redis에 캐시되어 조회 성능을 확보하지만, **쓰기 요청이 들어올 때마다 WebSocket 서버가 `created_at + 24h`를 실시간 계산하여 캐시값과 무관하게 최종 판정**한다.
- 캐시와 실제 판정이 다를 경우(워커 지연 등) 실제 계산값을 따르고, 비동기로 캐시를 갱신한다.

### 3.3 Purge 안정성

- Purge Worker는 배치 단위(예: 1회 최대 500개 방)로 처리하며, 각 방 삭제는 트랜잭션으로 원자적으로 처리한다.
- 실패 시 재시도 큐(예: SQS 또는 Redis 기반 재시도 리스트)에 적재하여 최대 3회 재시도, 이후 알림 발송 후 수동 개입.

## 4. HOT 알고리즘 처리 구조

PRD §5의 계산식과 10초 주기 재계산을 시스템으로 구현합니다.

### 4.1 데이터 소스

| 지표 | 소스 |
| :--- | :--- |
| 현재 동접자 수 | WebSocket 서버가 방별 연결 수를 Redis Hash(`room:{id}:conn_count`)에 실시간 갱신(연결/해제 시 INCR/DECR) |
| 최근 5분 채팅 수 | Redis Stream의 타임스탬프 기반 슬라이딩 카운트, 또는 별도 Sorted Set(`room:{id}:msg_times`)에 타임스탬프를 저장 후 5분 이전 항목을 주기적으로 제거(ZREMRANGEBYSCORE) |
| 최근 5분 반응 수 | 채팅 수와 동일한 방식의 별도 Sorted Set |

### 4.2 스코어 계산 워커

- HOT Score Worker가 10초마다 전체 LIVE 방을 순회하며 위 3개 지표를 조합해 Score를 계산하고, 결과를 Redis Sorted Set `hot:ranking`에 `ZADD`로 갱신한다.
- 상위 3개 조회는 `ZREVRANGE hot:ranking 0 2`로 O(log N) 처리되어 방 수가 많아져도 조회 성능이 유지된다.

### 4.3 어뷰징 방어 구현

- PRD §5.2의 "60초 내 재연결은 동일 접속으로 간주" 규칙: 연결 해제 시 즉시 DECR하지 않고, 60초 지연 후에도 재연결이 없을 때만 DECR하는 지연 처리 방식(Redis에 `disconnect_pending` 임시 키 + TTL 60초)으로 구현.
- 급격한 스코어 상승 플래그(300% + 절대값 기준)는 HOT Score Worker가 계산 직후 직전 값과 비교하여 판정, 조건 충족 시 별도 관리자 검토 큐(PostgreSQL 테이블 또는 SQS)에 적재.

## 5. 신고·모더레이션 처리 구조

- **1차 필터(금칙어)**: WebSocket 서버가 메시지 수신 즉시 동기 체크(인메모리 트라이 구조 또는 Redis 기반 사전 조회) 후 위반 시 즉시 거부 — 지연시간에 영향을 주지 않도록 O(1)~O(log N) 수준으로 유지.
- **2차 필터(AI 맥락 감지)**: 메시지 전송은 그대로 처리하되, 비동기 큐(SQS 등)로 별도 모더레이션 서비스에 전달하여 사후 감지. 위반 시 해당 메시지를 블라인드 처리하는 이벤트를 다시 WebSocket 채널로 발행.
- **신고 누적 처리**: 신고는 REST API로 접수되어 PostgreSQL에 기록되며, 동일 메시지에 5건 이상(10분 이내) 누적 시 트리거가 자동 블라인드 이벤트를 발행(PRD §6.2 기준과 일치).

| 구분 | LIVE 구간 | READ 구간 |
| :--- | :--- | :--- |

| 이중화 | Redis Cluster (3 shard 이상, 각 shard 복제본 1개) | Primary-Replica 구조, 조회는 Replica로 분산 |

## 7. 인프라 구성 (AWS)

- **컴퓨트**: ECS/Fargate — WebSocket 서버, REST API 서버, 각종 워커(Lifecycle/Purge/HOT Score)를 독립 서비스로 분리 배포. 워커 장애가 실시간 채팅에 영향을 주지 않도록 격리.
- **오토스케일링 트리거**: WebSocket 서버는 **활성 커넥션 수** 기준(예: 인스턴스당 1만 커넥션 초과 시 스케일아웃), REST API는 CPU/요청 수 기준.
- **Redis**: ElastiCache for Redis (Cluster Mode Enabled) — 샤딩으로 단일 노드 병목 방지.
- **DB**: RDS for PostgreSQL — Multi-AZ + Read Replica 최소 1개(READ 상태 조회 트래픽 분산).
- **CDN**: CloudFront — 이미지, OG 카드, 정적 자산 캐싱. OG 카드는 PRD §8.2에 따라 TTL 5분으로 설정.
- **메시지 큐**: SQS — 모더레이션 큐, Purge 재시도 큐, 관리자 검토 큐.
- **모니터링**: CloudWatch 기본 + 추후 Datadog 등 APM 도입 검토(운영 문서에서 상세화).

## 8. 보안 및 개인정보 처리 구조

- 모든 클라이언트-서버 통신은 TLS(WSS/HTTPS) 강제.
- 세션 토큰은 HttpOnly/Secure 쿠키로 발급하며, WebSocket 연결 시 최초 핸드셰이크에서만 검증 후 커넥션에 바인딩(매 메시지마다 재검증하지 않아 지연시간 최소화, 단 토큰 만료 시 강제 연결 종료).
- IP 로그는 별도 로그 저장소(예: PostgreSQL 별도 테이블 또는 S3)에 30일 TTL로 보관 후 자동 파기 배치 실행(PRD §5.3, §10 일치).
- 채팅 메시지는 저장 전 서버 단에서 XSS 방지 sanitize 처리(HTML 태그 이스케이프).

## 9. 장애 대응 및 가용성 전략

| 장애 시나리오 | 대응 |
| :--- | :--- |
| WebSocket 서버 인스턴스 다운 | ALB 헬스체크로 자동 제외, 클라이언트는 재연결 로직으로 다른 인스턴스에 자동 연결. 무상태 설계 덕분에 세션 손실 없음(Redis에 상태 보존). |
| Redis 노드 장애 | Cluster Mode의 복제본으로 자동 페일오버. HOT 스코어는 일시 정확도 저하 허용(치명적이지 않음). |
| PostgreSQL Primary 장애 | Multi-AZ 자동 페일오버. READ 상태 방은 일시적으로 읽기 전용 지연 발생 가능(허용 범위). |
| Lifecycle Worker 중단 | §3.2 이중 검증 원칙에 의해 실제 서비스 로직(쓰기 권한 판정)은 영향받지 않음. 캐시 상태만 지연 갱신되므로 데이터 정합성 문제 없음. |
